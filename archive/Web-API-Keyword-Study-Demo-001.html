Before you begin

Web APIs are an important part of modern software development. They enable communication between applications and are widely used in websites, mobile applications, and distributed systems.

Understanding Web APIs requires progressing from their basic purpose to how requests are processed, how interfaces are designed, and how real-world reliability problems are handled.

QUESTION 01 / INTRODUCTION

What is a Web API, and how does it differ from the broader concept of an API?

Full answer and explanation⌄
CORRECT ANSWERA — An API is a way for software components to communicate, while a Web API is a type of API that uses web technologies such as HTTP.

API stands for Application Programming Interface. It is a set of rules that explains how one piece of software can use the features or services provided by another piece of software.

For example, imagine you are developing a Java application. Your program may use methods provided by a Java library. You do not need to know how every method works internally. You only need to know which method to call, what information to provide, and what result to expect. This is one example of using an API.

A Web API follows the same basic idea, but communication happens through web technologies, most commonly HTTP.

Consider an e-commerce application. When a customer opens a product page, the application may send an HTTP request to a Web API asking for the product details. The backend receives the request, processes it, and returns information such as the product name, price, and availability.

The important distinction is that API is the broader concept, while Web API is a specific type of API. APIs do not always require HTTP, a web server, or even a network connection.

Why the other choices do not fit

B: Reverses the distinction. A Web API often communicates over a network; a general API need not.

C: Confuses Web APIs with the job of building web pages. A Web API commonly returns data, not an entire webpage.

D: Confuses an interface with database storage rules and user-interface design.

Remember: Every Web API is an API. Not every API is a Web API.

QUESTION 02 / FUNDAMENTALS

Why do software applications use Web APIs, and what problems would arise if applications communicated without well-defined interfaces?

Not answered
Choose the best answer
Your explanation is directly below the options.
Full answer and explanation⌄
CORRECT ANSWERC — Web APIs define how applications request and exchange information, reducing confusion when different systems communicate or change.

Software applications often need information or services provided by other applications. A shopping website may need product information, a mobile application may need customer account details, and a payment service may need order information.

A Web API provides an agreed way for these applications to communicate.

For example, suppose an e-commerce backend provides an endpoint:

GET /products/101

The frontend knows that sending this request asks for information about product 101. The backend knows which request it must handle and what kind of response it should return.

Both applications follow an agreed interface. The frontend does not need to understand how the backend stores products or how its internal code is organized.

Without a well-defined interface, several problems can occur. An application might send a product ID using one field name while the receiving application expects another. A developer might change the structure of a response without realizing that several other applications depend on it. Different teams might implement the same operation in incompatible ways.

These differences can cause failed requests, incorrect information, and additional work whenever an application changes.

A well-designed Web API reduces these problems by defining the available operations, the information clients must send, the responses they can expect, and how errors are communicated.

It also allows several clients, such as a website and a mobile application, to use the same backend services without needing to share the same internal code.

Why the other choices do not fit

A: A server cannot safely understand every arbitrary input. Client and server need agreed expectations.

B: A Web API does not mean that every client should access the same database directly.

D: A Web API does not remove the need for servers or backend processing.

Remember: Clear, consistent interfaces let different applications work together even when their internal code is different.

QUESTION 03 / WORKING MECHANISM

What happens from the moment a client sends an HTTP request to a Web API until it receives a response?

Not answered
Choose the best answer
Your explanation is directly below the options.
Full answer and explanation⌄
CORRECT ANSWERD — The client sends an HTTP request, the server identifies and processes the operation, and the server returns an HTTP response with the result or an error.

When a client communicates with a Web API, the communication usually follows a request-and-response process. Consider a customer opening the details of a product in an e-commerce application.

Step 1 — The client creates an HTTP request.

The customer selects a product. The application prepares a request containing the HTTP method and the address of the resource it needs.

GET /products/101

Here, GET indicates that the client wants to retrieve information. /products/101 identifies the requested product.

Step 2 — The request reaches the server.

The server receives the HTTP request and identifies which part of the backend application should handle it.

For example, a request for /products/101 may be directed to the part of the application responsible for product operations.

Step 3 — The server checks the request.

Before performing the operation, the server may check whether the request is valid and whether the client has permission to perform it.

The checks depend on the operation. Viewing a public product might not require authentication, while accessing a customer's private order details usually would.

Step 4 — The server performs the required work.

The backend executes the logic needed for the request. In this example, it may retrieve product 101 from a database.

The database might contain information such as the product name, description, price, and quantity available.

Not every Web API request needs database access. Some operations perform calculations, communicate with another service, or return information already available to the server.

Step 5 — The server prepares an HTTP response.

After processing the request, the server creates a response.

A successful response might contain a status code of 200 OK and a JSON response body:

{
  "id": 101,
  "name": "Wireless Mouse",
  "price": 25.99,
  "available": true
}

If the requested product does not exist, the server may instead return 404 Not Found.

The HTTP status code communicates the outcome, while the response body can provide the requested data or additional information about an error.

Step 6 — The client receives and uses the response.

The frontend reads the HTTP response and decides what to display.

If the response is successful, it may show the product details. If the product was not found, it may display an appropriate error message.

The complete process is therefore not simply sending and receiving data. It includes identifying the requested operation, checking the request, performing the necessary work, and communicating the outcome through a structured HTTP response.

Why the other choices do not fit

A: A client usually talks to the API, not straight to the backend database.

B: The server normally processes the request before deciding what response to send.

C: Forwarding requests to another application is not always needed; the server must still identify the operation.

Remember: The client requests an operation, the server processes it, and the HTTP response tells the client what happened.
